# Mirror Agent 开发日记（2026-04-04 至 2026-04-06）

## 这两天我们在做什么

这两天的工作，核心不是单点写功能，而是在把 `Mirror Agent` 从“能跑起来的原型”往“更像镜子里住着一个人”的方向推。  
一开始先把项目骨架、网页端、语音链路、记忆、提醒和测试基线搭起来；随后重点补了几条最影响体验的链路：外接摄像头优先、提醒跨端同步、面膜计时交互、多模态看脸表达，以及角色感和动画反馈的一致性。

这份日记覆盖两个层面：

- 已提交到仓库的内容：截至 `2026-04-05`
- 当前工作区里已经完成、但还没形成新提交的优化：截至 `2026-04-06`

## 2026-04-04：先把项目骨架搭稳

### 当天遇到的问题

项目刚导入时，虽然目标很明确，但还没有一条完整闭环：

- 语音、网页、图片分析、提醒、记忆都还是分散需求，缺少统一入口
- 角色设定、知识库、记忆文件和工具调用之间还没有真正串起来
- 如果后面直接往上堆功能，很容易进入“demo 能演、但系统不好维护”的状态

### 我做了什么

先完成了第一版可运行底座，主要包括：

- 搭起 `agent / tools / memory / webapp / voice input / voice output / reminders` 这些核心模块
- 建立网页聊天、图片分析、语音输入输出、提醒调度、日记写入的基础链路
- 准备了 `README`、规格文档、技术方案和较完整的测试基线
- 给后续的多模态、提醒、平板动画和角色设定留出了扩展口

### 结果

到这一步，项目已经从“概念”进入了“可以持续迭代”的状态。后面两天遇到的大多数问题，都是建立在这个基础版能稳定跑通之后才暴露出来的。

## 2026-04-05：把最影响体验的几条链路补起来

### 问题 1：网页端只能吃系统默认摄像头，外接摄像头体验不稳定

这是最早暴露出来的明显问题。网页端原本直接走 `getUserMedia({ video: true })`，浏览器会优先打开系统默认镜头，导致：

- 想优先用外接摄像头 `1080P USB Camera` 时不稳定
- 页面上看不到当前到底连的是哪个摄像头
- 摄像头断开后，会话很容易中断

### 我修复了什么

- 增加了视频设备枚举和优先选择逻辑，优先连接外接摄像头
- 在页面里显示“当前摄像头”状态，避免用户不知道实际连接到哪路镜头
- 缓存最近一次命中的 `deviceId`，减少重复选择成本
- 监听 `devicechange` 和视频轨道 `ended`，在外接镜头断开时自动恢复到可用镜头
- 给镜头选择、镜头恢复、镜头状态提示补上了前端逻辑

### 这次修复带来的变化

摄像头从“能开”变成了“更像真实设备管理”：

- 能优先命中外接镜头
- 能感知设备切换
- 能在异常时自动兜底，而不是让整条视频问答链路直接断掉

---

### 问题 2：提醒虽然能调度，但前端和平板态之间是断开的

提醒原本更多停留在服务端调度器里，前端与平板动画页没有真正共用状态，所以会有几个问题：

- 提醒创建后，展示端感知不及时
- 提醒触发后，聊天页和平板页不能稳定同步
- 一些场景只能本地凑效果，跨页面、跨设备状态一致性不够

### 我修复了什么

- 在后端加了 `TabletStateStore`，作为展示态的统一状态容器
- 增加 `/api/tablet-state` 读写接口
- 前端把本地 `localStorage`、`BroadcastChannel` 和服务端状态同步串起来
- 把 `scene / reminder / lastTriggeredReminder` 做成共享状态
- 聊天、图片、语音、流式语音接口都补上 `scheduled_reminder` 回传
- 到点提醒时，把提醒内容、音频地址、触发时间和 UI 效果一起同步出去

### 这次修复带来的变化

提醒不再只是“后台记住了”，而是开始真正驱动前台状态：

- 平板页能同步看到提醒和动画场景变化
- 聊天页和展示页的反馈开始连成一条链
- 后续做首页展示化时，状态复用成本会低很多

---

### 问题 3：面膜计时交互不自然，提醒识别也偏窄

一开始的提醒解析比较朴素，主要靠“提醒 + 数字分钟”这类文本命中，问题很明显：

- “我在敷面膜”这种自然表达不一定能被识别成计时场景
- 中文分钟表达覆盖不全
- AI 主动问“要不要计时”后，用户说“好呀/开始吧”之类的确认语，不一定能接住
- 重复说同一句提醒时，可能产生重复调度

### 我修复了什么

- 扩展提醒解析逻辑，支持中文数字分钟和更多自然语言触发词
- 增加面膜场景检测，识别“正在敷面膜”这类表达
- 增加 `pending_timer_offer` 状态，让“先询问、再确认、再调度”这条链路成立
- 补充肯定/拒绝意图识别，接住“好呀”“开始吧”“先不用”这类回答
- 在提醒调度器里加入去重逻辑，避免同一提醒反复堆积
- 到点提醒时，为面膜类提醒附加 `glow` 效果，增强展示反馈

### 这次修复带来的变化

提醒能力开始更像“闺蜜顺手帮你记着”，而不是“一个只能识别固定句式的闹钟接口”。

---

### 问题 4：多模态看脸时，回答太像“在分析图片”

这块是体验里很违和的一点。最初多模态回答更像传统图像分析助手，容易出现下面这些问题：

- 会说“照片里”“图片中”“上传这张图”
- 用户说“这里”“这块”“这个痘”时，不一定能落到具体脸部区域
- 画面不稳时容易回复“没看清”“再发一张”
- 整体不像“对着镜子直接看着本人说话”

### 我修复了什么

- 在系统提示和多模态用户提示里强化“照镜子说话”的表达约束
- 给“这里/这块/这个痘”增加区域落点要求，尽量明确到额头、脸颊、鼻翼、下巴等范围
- 调整多模态用户文本构造方式，把完整视角和局部视角的提示拼进去
- 清理回复中的媒介词和“重拍/再发一张/没看清”类表述
- 对画面不够理想时的兜底文案做了统一，让回复依然自然
- 针对摄像头开启状态下的追问，改成更像实时陪看的说法

### 这次修复带来的变化

多模态回复开始更贴近这个产品的核心设定：不是在“看图”，而是在“照镜子聊天”。

## 2026-04-06：继续补角色感、模型默认值和动效反馈

这部分是当前工作区里已经完成、但还没形成新提交的优化。

### 问题 5：角色语言已经可用，但还不够像“住在镜子里的护肤闺蜜”

前面几轮跑下来，我们已经能得到还算顺畅的回复，但角色感还有几个短板：

- 第一次见面的开场不够自然
- 对用户的了解维度偏窄，容易直接进入“护肤问答”
- 打招呼、告别、面膜陪伴这些高频场景的语气还不够生活化
- 角色虽然有人设，但“陪伴感”和“生活感”还可以更强

### 我修复了什么

- 重新补强了 `soul.md`，明确第一次见面、起名、了解用户、陪伴语气和边界
- 增加“作息、吃饭、护肤习惯一起养稳”的长期陪伴方向
- 补了打招呼、告别、面膜、情绪接住、中医食养视角等高频场景规则
- 调整首页默认文案和首条消息，让开场更自然地引导用户介绍自己
- 补了对应的 `agent` 和前端契约测试，防止后续提示词回退

### 这次修复带来的变化

角色不只是“能回答护肤问题”，而是更接近“有脾气、有态度、能慢慢懂你的人”。

---

### 问题 6：平板动画和语义事件之间的映射还不够细

之前平板页主要覆盖 `startup / listening / thinking / reply / idle` 这些大状态，但对“打招呼”和“告别”这种轻量情绪事件没有差异化反馈。

### 我修复了什么

- 在主前端里增加了 `resolveReplyScene`，根据文本识别 `hello / halou / 你好 / 再见 / 晚安` 等语义
- 新增 `greeting / farewell` 两个过渡场景
- 在平板动画侧加入 `ear-wiggle` 变体，并补了对应 CSS 动画
- 为这些场景补上前端契约测试，确保脚本和样式都在

### 这次修复带来的变化

现在平板动画开始不仅跟“系统状态”联动，也能跟“对话语义”联动，拟人感会更强。

---

### 问题 7：默认模型参数偏保守，语音转写默认值也有优化空间

这轮体验里，还有两个很实际的问题：

- 视觉模型默认值不够贴合当前多模态使用场景
- 本地 Whisper 默认还是 `base`，在现有使用预期下，准确率和稳定性还有提升空间

### 我修复了什么

- 把 AIPing 路线下默认视觉模型改成 `Doubao-Seed-2.0-pro`
- 新增 `test_config.py`，锁住这个默认值，避免以后被无意改回去
- 把本地 Whisper 默认模型从 `base` 调整到 `small`
- 增加 `MIRROR_AGENT_WHISPER_MODEL` 环境变量覆盖能力
- 更新 `README` 和 `voice_input` 相关测试，明确默认值和可配置方式

### 这次修复带来的变化

模型默认配置更贴近当前项目的真实使用方式，也给后续做环境切换和调优留了出口。

## 这两天最有代表性的收获

### 1. 真正难的不是功能点，而是链路感

很多问题看上去只是一个按钮、一句提示词、一个提醒字段，但真实影响的是整条体验链路。  
比如提醒这件事，不只是“调度成功”就结束了，它还要穿过 Agent、Web API、前端状态、平板展示和音频播报。

### 2. “像人”这件事，往往靠小处积累

角色感不是改一段 prompt 就能立刻成立的。  
它来自开场怎么说、看脸时怎么说、面膜要不要先问一句、告别时会不会轻轻叮嘱、动画会不会在正确时机做出小反应。

### 3. 现在的系统已经开始有“展示型产品”的雏形了

虽然首页展示化改造还没完全落地，但摄像头、提醒、状态同步、平板动画和语义反馈这些底层能力已经在成形，后面做“镜面感更强的首页”就不会是重新推倒来过。

## 后续还有哪些优化空间

### 1. 完成首页展示化改造

这块规格已经写了，但实现还没收尾。后续可以继续推进：

- 把根路径真正切成“展示首页”
- 把开发测试页迁到单独路由，比如 `/lab`
- 把复杂输入控件从首页抽走，只保留展示必要元素

### 2. 提醒状态做持久化

现在提醒调度和展示状态主要还是进程内存态：

- 服务重启后会丢
- 多实例部署时不能天然共享

后面可以考虑落到文件、SQLite 或 Redis，让提醒更可靠。

### 3. 平板态同步从轮询/共享存储升级为实时通道

现在已经能同步，但还可以更进一步：

- 用 WebSocket/SSE 统一推送状态
- 减少前端补偿逻辑
- 提高跨设备展示的一致性和实时性

### 4. 多模态看脸从“提示词约束”升级到“更结构化的视觉能力”

目前主要还是靠提示词和多视角组织来增强区域表达，后面还可以继续补：

- 更稳定的局部区域策略
- 更清晰的观察结构化输出
- 面膜、泛红、痘痘等常见场景的专项评估模板

### 5. 角色评测体系还需要更系统

现在已经开始用契约测试守住一部分人设和文案，但还不够：

- 可以补更多对话回归样例
- 可以做 greeting / reminder / image chat / goodbye 的场景回放
- 可以把“太像客服”“太像看图助手”的回复作为反例长期压测

### 6. 语音链路还可以继续降延迟和提稳定性

比如：

- 更好的 VAD / 静音截断策略
- 更稳的浏览器录音兼容性
- 更明确的异常提示和恢复策略

## 小结

如果用一句话总结这两天的进展，那就是：

我们不是单纯给 `Mirror Agent` 加了几个功能，而是在把它从“原型工具”慢慢修成“有镜中陪伴感的交互体”。

已经落下去的关键修复，主要集中在：

- 外接摄像头优先与恢复
- 提醒创建、同步、触发这条完整链路
- 面膜计时和自然语言提醒识别
- 多模态看脸的说话方式
- 角色感、语义动画和默认模型配置

后面最值得继续投入的方向，是首页展示化、提醒持久化、实时同步和更稳的多模态/语音体验。
