## 一、这三天我们到底在构建什么样的 Agent

从设计文档和技术方案看，这个 Agent 从一开始就不是“会聊天的护肤问答框”，而是一个更完整的本地陪伴式系统，目标包括：

- 有明确人格，而不是通用 AI 助手
- 有长期记忆，而不是一次性对话
- 能接文字、图片、语音和镜头帧，而不是单模态输入
- 能调用工具，而不是把所有事情都塞进一轮 prompt
- 能形成 diary / profile / insights 这样的本地记忆闭环
- 能接提醒、自拍分析、知识检索和趋势判断这类垂直能力

所以这三天构建的重点，其实是把下面这条主链路搭出来：

`用户输入 -> MirrorAgent 路由 -> system prompt + memory + short history -> model / tools -> reply -> history / reminder / diary`

当前代码里，这条链路主要落在这些文件：

- `mirror-agent/agent.py`
- `mirror-agent/tools.py`
- `mirror-agent/memory.py`
- `mirror-agent/webapp.py`
- `mirror-agent/reminders.py`
- `mirror-agent/soul.md`
- `mirror-agent/config.py`

## 二、当前 Agent 的实际架构

先把现在已经成型的 Agent 结构说清楚，后面的日记会围绕这些模块展开。

### 1. 编排中枢：`MirrorAgent`

`MirrorAgent` 现在负责的事情很多，属于当前系统真正的业务核心：

- 初始化 `config / memory / soul prompt / provider client / tools / reminders`
- 保存短期会话历史 `history`
- 管理临时状态，如：
  - `awaiting_photo`
  - `pending_timer_offer`
  - `last_scheduled_reminder`
- 组装系统提示词
- 根据输入类型路由：
  - 普通文本
  - 本地图片路径
  - 语音转文字
  - 携带 `image_paths` 的多模态回合
  - 结束会话
  - 提醒场景
- 驱动 tool loop
- 对回复做“口语化、去媒介词、限长”处理

换句话说，Agent 现在既是 orchestrator，又承担了一部分 intent parser、reply normalizer 和 state holder 的职责。

### 2. 工具层：`MirrorTools`

当前的工具集合已经覆盖了 Agent 的几条关键能力：

- `skin_analyze`
- `memory_read`
- `memory_write`
- `skincare_knowledge`
- `trend_analyze`
- `schedule_reminder`

这层的价值在于：把“模型推理”和“本地能力”统一到一套 function tools 机制里。  
Agent 不需要硬编码每类任务都怎么答，可以在需要时走工具。

### 3. 记忆层：`MemoryStore`

记忆现在是 Markdown-based，本地可读可编辑，分三层：

- `profile.md`：稳定画像
- `diary/YYYY-MM-DD.md`：每日互动记录
- `insights.md`：7 天以上才值得沉淀的模式

这个设计很适合 MVP，因为它：

- 可读
- 可手工修
- 易于调试
- 没有数据库门槛

### 4. 交互承接层：`webapp.py`

Agent 并不是直接面对浏览器，而是通过 `webapp.py` 接住各种入口：

- `/api/chat`
- `/api/image`
- `/api/voice-chat`
- `/api/voice-chat-stream`
- `/api/reminders/due`
- `/api/tablet-state`

这一层的作用是把浏览器输入变成 Agent 能吃的结构化上下文，再把 Agent 输出转回前端可消费的 JSON / NDJSON / 音频。

### 5. 提醒层：`ReminderScheduler`

提醒目前是内存版调度器，负责：

- 根据分钟数创建提醒
- 在轮询时返回已到期提醒
- 做基本的重复提醒去重

这层已经够支撑 demo 和单机体验，但还不够支撑“长期 personal agent”。

## 三、2026-04-04：把 Agent 的骨架先搭出来

### 1. 当天的核心目标

`2026-04-04` 这一天的任务，本质上是回答一个问题：

“我们要怎样用尽量轻的本地工程，把一个有人格、有记忆、能调工具的护肤陪伴 Agent 跑起来？”

这一天更偏架构搭建，而不是体验打磨。

### 2. 当天做了哪些事

#### 2.1 搭起了 `MirrorAgent` 的主循环

这一步是最关键的。当天把 Agent 的最小闭环先搭起来了：

- 读取 `soul.md`
- 读取 memory 上下文
- 拼接最近几轮 history
- 接入 provider client
- 调用模型
- 支持 tool calls
- 把最终回复写回 history

这意味着 Agent 不再只是“给模型喂一句话拿一句话”，而是开始具备：

- 人格上下文
- 记忆上下文
- 工具上下文
- 会话连续性

#### 2.2 定下了人格文件 `soul.md`

这一步看起来像 prompt 编写，实际上是 Agent 产品能力的一部分。  
因为在这个项目里，“人格”不是 UI copy，而是编排层的核心输入。

首版人格至少先定义了：

- 她是谁
- 她不是谁
- 她如何和用户第一次见面
- 她该怎么说话
- 她对护肤、情绪、边界的基本态度

没有这层，人设就会在多轮对话里很快散掉。

#### 2.3 搭起了本地记忆结构

这一天把 `MemoryStore` 的第一版建立起来，至少完成了：

- memory 目录自动初始化
- profile / insights / diary 的文件组织
- 最近 diary 读取
- profile 和 insights 的读取
- memory context 组装

这是后面所有“她会记住你”的前提。

#### 2.4 把工具体系接进来

这一天定义并接入了第一批工具：

- 自拍分析
- 记忆读取
- 记忆写入
- 护肤知识检索
- 趋势分析
- 提醒创建

也就是说，Agent 从第一天开始就不是“靠 prompt 假装会很多事”，而是有意识地走工具化路线。

#### 2.5 做了 provider 适配

这一步也是架构里很重要但容易被忽视的部分。

当天就保留了双 provider 方向：

- 本地 `ollama`
- 第三方 OpenAI-compatible 通道

这让 Agent 能在：

- 本地优先实验
- 需要更强模型时切换第三方

之间保持一定弹性。

#### 2.6 补了测试底座

`2026-04-04` 并不是只在写实现，也同步补上了测试基线，至少锁住了这些能力：

- memory 初始化和读取
- system prompt 组装
- diary 写入
- 结束语识别
- 部分 web / voice / tools 契约

这让后面两天的重构和提示词大改不至于完全裸奔。

### 3. 这一天暴露出来的问题

虽然骨架成型了，但第一天其实已经埋下了后面要修的很多问题：

#### 3.1 `MirrorAgent` 职责开始偏重

第一天为了先跑通，很多东西都先收口在 `agent.py` 里了。  
这对 MVP 很合理，但副作用是：

- 路由在这里
- 状态在这里
- 回复后处理在这里
- 多模态用户消息构造也在这里

后续功能一多，`agent.py` 很容易变成“什么都懂一点的大文件”。

#### 3.2 记忆写入时机偏晚

第一版 memory 更偏“会话结束后再写入”。这带来的风险很直接：

- 用户中途关页面会丢信息
- 一些关键事件没有即时沉淀
- profile / insight 更新偏被动

这个问题在技术方案里也已经明确被标出来了。

#### 3.3 会话状态是进程内的、全局的

第一版 `history` 是内存里的 list，适合单用户 demo，但不适合真正产品化：

- 服务重启会丢
- 多用户无法隔离
- 多窗口共享语义不清晰

#### 3.4 工具文件开始膨胀

`tools.py` 从第一天起就承担了很多不同类型的职责：

- 视觉分析
- 记忆总结
- 知识检索
- 趋势分析
- 提醒创建

这意味着如果不及时拆，后面维护成本会越来越高。

## 四、2026-04-05：开始解决“它能跑”和“它像镜子里的人”之间的落差

如果说 `2026-04-04` 是把 Agent 搭出来，`2026-04-05` 更像是在补它真正可用的链路。

### 1. 重点修复方向一：多模态回合真正接进 Agent

#### 当时的问题

虽然系统已经有图片/镜头方向，但实际体验里，多模态对话还不够“像照镜子聊天”：

- 用户说“这里”“这块”“这个痘”时，回复不一定落得准
- 模型容易说“照片里”“图片中”“这张自拍”
- 一旦画面不理想，容易滑回“没看清、再拍一张”
- 镜头模式和图片上传模式的说话方式没有拉开

#### 当天修了什么

这一天在 `agent.py` 里围绕多模态链路做了几件关键事：

- 增加 `_build_multimodal_user_text`
- 根据图片名给局部图打标签，如：
  - `完整画面`
  - `左脸颊局部`
  - `右脸颊局部`
  - `额头局部`
  - `鼻翼局部`
  - `下巴局部`
- 把“不要提图片/照片/镜头”“尽量落到具体区域”这类约束塞进多模态用户文本
- 增加 `_prepare_visual_reply` / `_normalize_visual_reply`
- 专门清洗媒介词、不确定前缀和“让用户重拍”的句式

#### 这一步为什么重要

因为它解决的不是“代码能不能返回结果”，而是产品设定有没有被守住。  
Mirror Agent 的核心不是图像问答，而是“照镜子时镜子里住着个人”。这一步是在把输出风格从图像分析助手往镜面陪伴体拉。

### 2. 重点修复方向二：面膜计时与提醒能力从固定句式走向自然语言

#### 当时的问题

第一版提醒更像“规则命中器”，而不像自然对话的一部分：

- 只对显式“几分钟后提醒我”更友好
- 对“我在敷面膜”这类自然表达接得不够好
- 用户确认“好呀 / 开始吧 / 先不用”时，状态链路不完整
- 重复提醒可能会重复堆

#### 当天修了什么

`agent.py` 和 `reminders.py` 这一天做了比较成体系的一轮增强：

- 增加 `parse_reminder_request`
- 增加中文分钟解析 `_extract_minutes` / `_parse_chinese_number`
- 增加面膜场景识别 `_is_mask_timer_request`
- 增加肯定/拒绝判断：
  - `_looks_like_affirmation`
  - `_looks_like_decline`
- 增加 `pending_timer_offer`
- 新增 `_capture_timer_offer` 和 `_handle_pending_timer_offer`
- 在 `ReminderScheduler` 里增加基于 `source_text / message` 的去重

#### 这一步为什么重要

这一步让 Agent 终于能处理一种非常典型的“生活化小事”：

- 用户不需要像操作闹钟一样说话
- Agent 可以先问一句，再接用户确认
- 提醒被纳入人格交互，而不是后台任务系统

这是陪伴型 agent 和工具型 agent 的典型分界点。

### 3. 重点修复方向三：提醒开始能穿过 Agent 传到前端展示层

#### 当时的问题

之前提醒更多停留在 scheduler 内部，Agent 创建了提醒，但前端不一定拿得到完整提示状态。

#### 当天修了什么

这一轮除了改 `webapp.py`，其实也是在改 Agent 能力边界：

- `MirrorAgent` 增加 `last_scheduled_reminder`
- 新增 `consume_last_scheduled_reminder`
- 在 `respond / respond_to_image / voice routes / stream routes` 中把 `scheduled_reminder` 透传给前端
- 提醒不仅被创建，而且能被 UI 消费、被平板态同步、被到点播报

#### 这一步为什么重要

它意味着“提醒”不再只是 Agent 内部的一次 tool call，而是开始成为完整交互结果的一部分。

### 4. 重点修复方向四：把展示状态从前端本地状态升级成 Agent 可驱动的共享状态

#### 当时的问题

平板页和聊天页之间的状态同步不稳定，Agent 虽然在对话里做出了动作，但展示侧并不总能接住。

#### 当天修了什么

在 `webapp.py` 增加了：

- `TabletStateStore`
- `/api/tablet-state` 读写接口

并把提醒、scene 和触发态统一成共享状态。

#### 为什么这也算 Agent 构建的一部分

因为对陪伴型 Agent 来说，输出不只是文字。  
当 Agent 说“我提醒你了”，如果展示层接不住，这个能力在用户感知里就是断的。  
所以这一步虽然代码落在 webapp，但本质是在补 Agent 的跨表面表达能力。

### 5. 这一天新增了哪些关键测试

`2026-04-05` 这次改动后，测试侧补得比较关键，主要锁住了：

- 提醒 payload 透传
- 平板共享状态读写与 merge
- 到点提醒的 UI effect
- 多模态 system prompt 约束
- 回复长度与句子上限
- 媒介词清洗
- 镜头开启场景下不再退回“发张照片”

这说明从这一天开始，我们已经不是只修“功能可用性”，而是在守体验契约。

### 6. 这一天留下的问题

尽管进展很大，但 `2026-04-05` 也把一些更深层问题暴露得更明显了：

#### 6.1 Agent 在用“提示词 + 文本清洗”兜底视觉表达

这很实用，但也说明视觉能力目前主要靠：

- prompt 约束
- 输入文本增强
- 输出文本清洗

而不是更结构化的视觉推理结果。  
短期够用，长期稳定性还不够。

#### 6.2 状态越来越多，但都挂在 Agent 实例里

现在 Agent 内部有：

- `history`
- `awaiting_photo`
- `pending_timer_offer`
- `last_scheduled_reminder`

这些状态在单用户单实例下没问题，但对未来 session 化非常不友好。

#### 6.3 tool loop 还缺更明确的任务边界

虽然 tools 已经接上了，但“什么时候走 tool、什么时候纯回复、什么时候优先规则路由”这件事，目前还是混合式的：

- 一部分靠前置 if/else
- 一部分靠 LLM tool call

这说明 intent router 还没有真正独立出来。

## 五、2026-04-06：开始补 Agent 的灵魂、默认参数和语义反馈

这一天的重点，不是重写架构，而是补“它到底像不像一个镜子里的闺蜜”。

### 1. 人格层继续深化：`soul.md`

#### 当时的问题

跑了几轮之后，会发现首版人设虽然成立，但还不够“活”：

- 开场仍有一点像引导流程
- 角色有设定，但长期陪伴方向还不够强
- 高频场景像问候、告别、面膜陪伴还不够具体
- 对情绪承接和生活化建议的约束还不够明确

#### 这一天补了什么

`soul.md` 这轮补得很细，重点包括：

- 默认对用户的亲昵称呼机制
- “把作息、吃饭和护肤习惯养稳”的长期目标
- 明确的“灵魂原则”：
  - 先共情再建议
  - 一次只聊一件事
  - 给一个具体行动
  - 敢有态度
- 第一次见面的更自然话术
- 了解用户的表达改得更像聊天
- 中医食养视角
- 面膜/计时场景
- greeting / goodbye 场景
- 照镜子看脸时的表达方式
- 边界进一步收紧

#### 为什么这很重要

这个项目里，人格不是“文案层”，而是 Agent 的策略层输入。  
人格文件一旦改变，会直接影响：

- build_system_prompt 内容
- 工具使用倾向
- 记忆写入方向
- 首轮互动体验

### 2. 把人格升级同步锁进测试

这一天不是只改 prompt，还补了测试，确认：

- system prompt 里包含第一次见面与陪伴语义
- system prompt 里包含中医食养映射
- 首页首条消息开始自然引导用户介绍自己

这件事很关键，因为人格类改动最容易“看着没报错，实际上体验已经退化”。

### 3. 配置层和语音输入默认值继续修

虽然这部分不是 `agent.py` 本体，但对 Agent 使用体验影响直接。

#### 做了什么

- 把 AIPing 默认视觉模型切到 `Doubao-Seed-2.0-pro`
- 新增 `test_config.py` 锁住这个默认值
- 把 Whisper 默认模型从 `base` 调到 `small`
- 增加环境变量覆盖能力 `MIRROR_AGENT_WHISPER_MODEL`

#### 为什么这算 Agent 构建的一部分

因为 Agent 体验不只由 prompt 决定，还取决于：

- 输入能不能听清
- 视觉模型能不能看懂
- 默认配置是否贴近当前主场景

如果默认参数不对，Agent 的“人格”和“记忆”再好也会被链路质量拖垮。

### 4. 从文本语义驱动展示反馈

这一天还有一条虽偏前端、但其实和 Agent 行为很相关的改动：

- 根据 reply 文本识别 greeting / farewell
- 推动平板页切到不同 scene

这说明 Agent 的输出开始不仅影响文字，还开始影响“角色表演”。  
从产品角度，这会进一步强化“镜子里有个陪你的人”的感受。

### 5. 这一天还留下了什么问题

#### 5.1 人格已经变强，但依然高度依赖 prompt

现在角色稳定性主要靠：

- `soul.md`
- `build_system_prompt`
- 回复长度限制
- 一些 post-process

这对 MVP 很好，但长期会遇到：

- prompt 越来越长
- 不同场景规则相互干扰
- 模型切换时表现波动

#### 5.2 记忆的“写”和“用”还不完全对称

现在记忆已经能读、能写、能汇总，但还存在一个问题：

- 写入依然偏摘要式
- 使用依然偏拼上下文式
- 缺少事件级别索引

所以“她记住了你”这件事已经成立，但还没有非常稳地进化成“她会在正确时机主动拿出来用”。

## 六、到 2026-04-06 为止，Agent 已经具备了哪些能力

把三天的工作收拢一下，到 `2026-04-06` 为止，这个 Agent 已经不是空壳了，至少具备下面这些能力：

### 1. 对话编排能力

- 能按输入类型做初步路由
- 能组装人格、记忆、短期 history
- 能处理 tool call 闭环
- 能支持流式和非流式回复

### 2. 角色一致性能力

- 有稳定人格来源 `soul.md`
- 有回复长度和话术约束
- 有看脸场景的表达清洗
- 有 greeting / goodbye / 面膜场景规则

### 3. 记忆能力

- 有 profile / diary / insights 三层结构
- 能做本地落盘
- 能在会话结束后产生日记
- 能写入自拍分析结果

### 4. 多模态能力

- 能吃图片路径
- 能吃浏览器音频 + 抓帧
- 能构造多视角上下文
- 能做自拍分析和简单历史对比

### 5. 提醒能力

- 能识别自然语言提醒
- 能支持面膜计时
- 能在确认后创建提醒
- 能把提醒结果传到前端和展示层

### 6. 工程可测试性

- 已经有一批围绕 agent 的单测和契约测试
- 关键人格约束、回复约束、提醒约束开始有护栏

## 七、当前 Agent 存在哪些问题

这一部分我会比“做了什么”更坦白一点，因为你后面肯定要继续推进。

### 1. 架构层问题

#### 1.1 `agent.py` 过重

现在 `MirrorAgent` 同时负责：

- 路由
- 状态
- prompt 组装
- tool loop
- 多模态 message 构造
- reply normalize
- reminder 过渡状态

这在 MVP 阶段是高效的，但继续加功能会越来越难维护。

#### 1.2 `tools.py` 也在变胖

`tools.py` 里同时混着：

- 视觉
- 记忆
- 知识库
- 趋势分析
- 提醒

一旦再加更多能力，比如周期提醒、结构化视觉评估、更多记忆策略，这个文件很快会失控。

#### 1.3 缺少真正独立的 intent router

现在 intent 识别是混合式的：

- 一部分正则/规则前置判断
- 一部分由模型决定 tool call

这让系统边界有时不够清晰，尤其是在：

- 自然语言提醒
- 看脸请求
- 普通闲聊
- 结束会话

这些边界靠得比较近的场景。

### 2. 状态与可靠性问题

#### 2.1 会话状态全在内存里

这包括：

- history
- awaiting_photo
- pending_timer_offer
- last_scheduled_reminder

问题是：

- 重启就没
- 无法天然支持多用户
- 多窗口共享不可控

#### 2.2 提醒仍然是内存版

这是当前最明确的可靠性短板之一：

- 服务重启提醒会丢
- 没有恢复机制
- 没有周期提醒
- 没有跨实例能力

#### 2.3 记忆写入偏后置

现在 diary 主要仍然依赖结束会话写入。  
如果用户没有明确结束、或者网页直接关闭，会丢掉一部分很重要的信息。

### 3. 体验与智能性问题

#### 3.1 多模态观察还偏“提示词增强”

当前确实已经改善很多，但底层仍然主要依赖：

- prompt 约束
- 文本注入
- 回复清洗

这让表现很依赖模型当前状态，不够结构化、不够稳。

#### 3.2 人格稳定性过度依赖长 prompt

现在人格越来越完整，这是好事；但同时也意味着：

- prompt 越来越长
- 规则越来越多
- 模型更容易被多个要求同时拉扯

后面如果继续往里塞规则，收益会开始递减。

#### 3.3 记忆提取还比较粗

`memory_write` 现在主要是：

- 模型总结
- 或本地关键词兜底

这让它能工作，但还不够细。  
比如：

- 哪些是用户稳定偏好
- 哪些只是当天随口一说
- 哪些值得马上写 profile
- 哪些应该等累计观察

目前还没有更明确的事件级判定。

#### 3.4 自拍分析和自然对话还没完全统一

现在有两条视觉路径：

- `respond_to_image` -> `tools.analyze_selfie`
- 多模态对话 -> `_respond_with_multimodal_context`

它们都在解决看脸问题，但策略并不完全统一。  
后面继续迭代时，可能会出现两条视觉链路风格越来越分叉的问题。

### 4. 工程与测试问题

#### 4.1 现在的测试更多是契约护栏，不是完整行为验证

目前测得比较好的是：

- 某些 prompt 是否包含关键句
- 某些字段是否回传
- 某些文案是否存在

但测得还不够的是：

- 长对话里的角色稳定性
- memory 实际引用质量
- 多轮提醒确认的复杂边界
- 多模态链路在真实模型上的稳态表现

#### 4.2 缺少 observability

现在如果 Agent 表现怪了，排查主要还是靠：

- 看代码
- 看 diary
- 看前端表现

但缺少系统化观测，比如：

- 这轮为什么走了某个分支
- tool call 是怎么决定的
- memory 命中了哪些内容
- 是哪一步把回复清洗掉了

## 八、后续如何优化

这部分我按“短期值得马上做”“中期该重构”“长期演进方向”来分。

### 1. 短期优化：先让 Agent 更稳

#### 1.1 把意图路由独立出来

建议从 `MirrorAgent` 里先拆一个轻量 `intent_router`，至少先明确：

- normal_chat
- image_observation
- camera_round
- reminder_create
- reminder_confirm
- session_end

这样能减少主流程里的 if/else 继续扩张。

#### 1.2 把提醒状态持久化

优先级很高。  
哪怕先不上 Redis，也建议先做：

- SQLite
- 或本地文件持久化

至少要支持：

- 服务重启恢复未完成提醒
- 唯一 id
- 到期扫描

#### 1.3 增加关键事件即时写 memory

建议不要只在结束时写 diary。  
可以先补几类立即写入：

- 用户给 agent 起名字
- 用户表达陪伴偏好
- 用户明确说自己的肤质/习惯
- 用户拒绝某种称呼

这样“记住你”这件事会更稳。

#### 1.4 给 Agent 增加调试日志

至少记录：

- 当前命中的 intent
- 是否进入 multimodal
- 是否创建/消费 reminder
- 是否触发 pending_timer_offer
- tool calls 列表

这对后面调行为会很有帮助。

### 2. 中期优化：让架构更可持续

#### 2.1 拆分 `tools.py`

建议按领域拆成：

- `memory_tools.py`
- `vision_tools.py`
- `knowledge_tools.py`
- `reminder_tools.py`

再由一个轻量 `MirrorTools` 做注册聚合。

#### 2.2 拆分 `agent.py`

可以逐步拆为：

- `conversation_orchestrator.py`
- `intent_router.py`
- `context_builder.py`
- `reply_postprocessor.py`

这样每块职责都会清晰很多。

#### 2.3 为会话引入 `session_id`

哪怕当前还是单用户，也建议提前留这个口：

- history 绑定 session
- pending 状态绑定 session
- memory 写入可以带来源 session

这样以后做多窗口、多端同步不会整套推倒。

#### 2.4 明确模型职责

建议把配置进一步拆成：

- `chat_model`
- `vision_model`
- `summary_model`

并允许：

- 不同 temperature
- 不同超时
- 不同降级策略

### 3. 长期优化：从 MVP agent 走向真正的 personal agent

#### 3.1 建事件级记忆层

保留 Markdown，但增加结构化 event store。  
比如每次关键互动存成事件：

- 时间
- 类型
- 置信度
- 是否已入 profile
- 是否已入 insight

这样 profile 和 insight 的生成会稳很多。

#### 3.2 统一视觉能力入口

后面建议把：

- 自拍分析
- 镜头帧分析
- 局部区域分析

统一成一套 vision service，输出结构尽量统一，比如：

- 区域
- 现象
- 轻重
- 风险提示
- 可用的自然回复草稿

#### 3.3 建立角色回归测试集

建议长期保留一组典型对话回放：

- 第一次见面
- 起名
- 介绍自己
- 看脸
- 面膜计时
- 心情不好
- 晚安收尾

每次改人格、模型或 tool loop 都跑一遍，避免角色悄悄变味。

#### 3.4 把 Agent 输出扩展成真正的多表面表达

现在已经有一点这个方向了，后面可以更明确：

- 文字回复
- 语音回复
- 平板 scene
- 提醒状态
- 首页展示状态

都由一个更明确的 agent response envelope 来承载，而不是分散在不同接口里各自拼字段。

## 九、我对这三天 Agent 构建的判断

如果要我直接下判断，我会这样总结：

### 1. 这三天最成功的地方

最成功的不是“加了多少功能”，而是早早把 Agent 做成了一个有边界的系统，而不是一坨 prompt demo。

具体体现在：

- 有明确的人格入口
- 有独立 memory 层
- 有工具层
- 有 provider 适配
- 有多模态路径
- 有提醒闭环
- 有测试护栏

这说明底子是对的。

### 2. 这三天最大的代价

代价是为了快速把 MVP 跑起来，很多职责先集中在 `agent.py` 和 `tools.py` 里了。  
这让速度很快，但也决定了下一阶段必须开始拆。

### 3. 当前最需要警惕的点

最需要警惕的是：不要继续只靠加 prompt 和加 if/else 往前推。  
现在已经到了一个节点，再往后如果不拆 intent、状态和 tool domain，后面每次改都可能牵一发而动全身。

## 十、小结

从 `2026-04-04` 到 `2026-04-06`，Agent 的构建经历了三个明显阶段：

### `2026-04-04`

把编排、人格、记忆、工具、provider 和测试底座搭起来，让 Agent 从无到有。

### `2026-04-05`

把多模态看脸、面膜计时、提醒同步和平板共享状态这些真正影响体验的链路补齐，让 Agent 从“能跑”走向“更像镜子里的陪伴者”。

### `2026-04-06`

继续打磨人格、默认模型和语义反馈，让 Agent 的灵魂、语气和表达更稳定。

如果下一阶段继续做，我建议优先顺序是：

1. 拆 intent router
2. 持久化 reminders
3. 增加关键事件即时 memory 写入
4. 拆 `tools.py` 和 `agent.py`
5. 引入 session 化状态
6. 建角色回归测试集

这六件事做完，Mirror Agent 才会从“很有感觉的 MVP”更稳地迈向“可持续进化的 personal agent”。
