# 镜子虾视频对话设计文档

## 背景

当前网页版已经具备：

- 文本聊天
- 图片上传分析
- 单击语音回合
- 实时字幕
- TTS 语音回复

缺的能力是“打开摄像头后，用户直接对着镜头问皮肤状态，镜子虾结合当前画面立即回复”。

## 目标

新增一个准实时视频对话模式，满足以下要求：

- 浏览器可打开本地摄像头并显示实时预览
- 用户不需要手动拍照
- 用户说完一轮话后，前端自动抓取当前摄像头画面
- 后端把“当前问题 + 当前画面”一起发给多模态模型
- 回复保留现有流式字幕和单通道 TTS
- 不要求连续视频流推理，避免引入高复杂度和高算力成本

## 方案选择

### 方案 A：连续视频流逐帧推理

优点：

- 最像真正视频通话

缺点：

- 当前本地模型链路不适合直接吃长视频流
- 前后端复杂度高
- 延迟和资源占用不稳定

### 方案 B：实时预览 + 每轮自动抓当前帧（推荐）

优点：

- 用户感知上接近视频对话
- 能复用现有语音、字幕、TTS 和图片理解能力
- 后端仍然只处理图片，不需要引入视频编解码链路

缺点：

- 不是严格意义上的逐帧视频理解

### 方案 C：打开摄像头后仍要求手动点拍照

优点：

- 实现最简单

缺点：

- 交互不自然，不符合“视频对话”预期

## 决策

采用“实时预览 + 每轮自动抓当前帧”的准实时视频对话方案。

## 架构

### 前端

- 在现有页面新增摄像头控制区
- 增加 `video` 预览、隐藏 `canvas`、打开/关闭摄像头按钮
- 语音回合结束时，如果摄像头已开启，自动从 `video` 抓当前帧并随语音一起上传
- 保持现有实时字幕和单通道语音播放逻辑

### 后端

- 扩展 `POST /api/voice-chat` 和 `POST /api/voice-chat-stream`
- 允许同时接收 `audio` 和 `frame`
- 将抓到的帧保存到临时目录
- 让 `MirrorAgent` 支持“带图流式回复”

### Agent

- 保留已有自拍分析路径不变
- 新增“带图聊天”的普通对话路径
- 当语音回合附带摄像头帧时，把该帧作为多模态输入拼进当前用户消息
- 回复仍遵守镜子虾人格、护肤红线和 Memory 规则

## 用户体验

页面新增：

- “打开镜头”按钮
- 摄像头实时预览区域
- 开启后的轻提示，例如“现在你说话时，我会顺手看一眼镜头”

一轮视频对话流程：

1. 用户点击“打开镜头”
2. 页面显示实时预览
3. 用户点击“点一下开口”并自然提问
4. 用户停下后，前端自动抓一帧
5. 后端结合该帧与问题生成回复
6. 页面流式显示文字字幕并语音播报

## 风险与约束

- 如果浏览器没有摄像头权限，只保留现有语音对话
- 如果画面为空、太暗或没拍到脸，模型应直接说明“没看清”
- 首版只抓 1 帧，不做多帧时序分析
- 纯 CLI 语音模式这轮不改，视频能力仅网页可用

## 测试策略

新增或更新测试覆盖：

- 页面包含摄像头控制与预览容器
- 前端会在语音回合中抓取视频帧
- 语音流接口支持附带 `frame`
- Agent 在带图流式回复路径中能接收图片列表
- 全量测试继续通过
